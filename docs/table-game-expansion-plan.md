# 追加テーブルゲーム実装計画

## 目的

`docs/table-game-expansion-spec.md` にまとめた追加テーブルゲームを、スマホ1台パスアンドプレイの実装ゲームとして段階的に追加する。

ゲーム体験は参考元の進行、勝敗条件、役職、採点にできるだけ準拠する。一方で、画面文言、ルール説明、お題、場所、尺度、カード文面、画像、音声、UIデザインはParty Deck用に自作する。

## 実装対象

初期追加対象は次の6ゲーム。2026-06-18に第2弾として、みんなと同じ回答とワンワード協力クイズを追加した。

| 優先 | 仮実装名 | 参考系統 | 実装理由 |
| ---: | --- | --- | --- |
| 1 | ワード潜入者 | Chameleon / Word Wolf / Imposter系 | 秘密情報、投票、推理だけで成立し、既存unitを流用しやすい |
| 2 | インサイダー推理 | Insider系 | 役職配布、答え配布、タイマー、投票がワンナイト人狼に近い |
| 3 | スパイロケーション | Spyfall系 | 場所データを作れば少ないUIで遊べる |
| 4 | 価値観メーター | Wavelength系 | ナンバートークと相性がよく、会話が盛り上がりやすい |
| 5 | ランキング回答 | Top Ten系 | ナンバートークの派生だが、協力採点として別ゲーム化できる |
| 6 | エセアーティスト | A Fake Artist Goes to New York系 | 体験は強いが、描画UIの検証コストが高い |
| 7 | みんなと同じ回答 | Majority / Herd系 | 秘密回答と集計だけで成立し、初見でも説明が短い |
| 8 | ワンワード協力クイズ | Just One系 | 秘密ヒント配布と重複取消がスマホ1台に向いている |

## 進め方

### Phase 1: 共通土台を整える

目的:

- 追加ゲームごとに `App.tsx` が肥大化しないようにする。
- 秘密確認、受け渡し、投票、タイマー、結果表示を共通化する。
- ゲーム同士が状態やデータで干渉しないようにする。

成果物:

- `src/features/passAndPlay` 相当の共通UI候補
- `src/games/<gameId>.ts` のゲーム別ロジック
- `src/data/<gameId>Topics.ts` のゲーム別データ
- ゲーム別smokeまたはunit test

### Phase 2: 権利に触れそうな素材を自作する

目的:

- 本家のルールブック本文、カード文面、お題リスト、画像、デザインを使わず、同じ遊び心地になる独自データを作る。

自作対象:

- 画面表示用の短いルール説明
- 詳細ルール説明
- お題、答え、場所、尺度、カテゴリ
- 役職説明、勝敗説明
- アイコン、色、カード風UI

成果物:

- ゲームごとのデータschema
- 初期データ
- 重複/類似チェックの運用メモ
- UI表示名と内部参照名の分離

### Phase 3: 1ゲームずつ実装する

実装順:

1. ワード潜入者
2. インサイダー推理
3. スパイロケーション
4. 価値観メーター
5. ランキング回答
6. エセアーティスト

各ゲームで必ずやること:

- `GameDefinition` 登録
- state/action/judge関数追加
- 秘密情報の直復帰防止
- 広告非表示フェーズの確認
- スマホ幅UI確認
- smoke/typecheck/build
- docs更新

### Phase 4: QAと友人テスト

目的:

- ルールを知らない友人が説明なしで開始できるか確認する。
- 1台のスマホを回すときに秘密情報が漏れないか確認する。
- 3人、4人、6人、8人で破綻しないか確認する。

確認観点:

- どの画面で誰に渡すか迷わない
- 秘密情報が前後のプレイヤーに見えない
- 投票や回答の完了条件がわかる
- もう一度遊ぶ導線がある
- 最終結果で何が起きたか説明できる
- テキストがスマホ幅ではみ出さない

### Phase 5: 後片付けと保守性改善

目的:

- 追加ゲームを急いで入れたことで増えた重複、仮置き、使われない型、肥大化した画面処理を整理する。
- 友人テストで得た改善点を反映し、次のゲーム追加が楽になる状態に戻す。

やること:

- `App.tsx` に残ったゲーム固有処理をゲーム別ファイルへ戻す。
- 共通化できる受け渡し、秘密表示、投票、タイマー、結果表示を整理する。
- 使われていない型、関数、CSS、データを削除する。
- 仮の文言、仮のお題、デバッグ表示を本番用へ差し替える。
- docsとtask-listの完了状態を更新する。
- smoke/typecheck/buildを通してからpushする。

## 共通設計方針

### ゲーム分離

- 追加ゲームは必ず独立した `gameId` を持つ。
- ゲーム状態は `SessionEnvelope` の `gameId` ごとに保存する。
- 他ゲームのstate型を直接参照しない。
- 共通化するのはUI部品、投票集計、タイマー、シャッフルなどの小さいunitに限定する。

### 秘密情報

- 受け渡し画面を挟む。
- 「見る」操作後だけ秘密情報を表示する。
- 閉じた後は同じ秘密情報へ直接戻さない。
- ブラウザバック、リロード、復帰時は受け渡し画面へ戻す。

### 広告

広告を出してよい:

- ホーム
- ゲーム設定
- ルール詳細を開いた状態
- 最終結果

広告を出さない:

- 秘密情報確認
- 回答中
- 投票中
- 描画中
- 受け渡し中
- タイマー進行中

### 結果表示

- 最終結果には必ず「勝敗または成否」「理由または根拠」「各プレイヤーの公開情報」「もう一度」「ゲーム一覧へ」を置く。
- 途中結果は次のラウンドへ進むボタンだけを置き、ゲーム一覧へ戻る導線は最終結果に限定する。
- 共通UIは `FinalResultActions`、`result-list`、`note`、`topic` の組み合わせを基本にする。ゲーム固有の採点、投票、描画プレビュー、正解位置は各ゲーム画面側で表示する。
- 広告は最終結果と、秘密情報を含まない途中結果だけに置ける。秘密、回答、投票、描画、受け渡しには置かない。

### 自作データ

本家に似せてよいもの:

- ゲーム進行
- 勝敗条件
- 採点構造
- 役職の機能
- 必要なカテゴリ構造

自作するもの:

- 表示文言
- ルール説明文
- お題文
- 場所名と説明
- 尺度カード
- 答えデータ
- アイコンと見た目

### 重複判定キー

- 初期実装では各データの `id` を `category-slug` 形式の安定キーにし、手作業データの `duplicateKey` 相当として扱う。
- smokeでは `id` と表示値（`secretWord`、`text`、`name`、尺度ラベルなど）の一意性を確認する。
- AI/cronでデータ追加する段階では、表示値をNFKC正規化、trim、空白除去、英字小文字化した `duplicateCandidateKey` を生成し、既存 `id`、表示値、近い別名に照合してから追加する。
- 同じ遊びになる候補は新規追加せず、既存レコードの別名、カテゴリ、メモへ寄せる。表現が近すぎる本家文面は採用しない。

## Definition of Ready

実装開始前に次を満たす。

- UI表示名が決まっている
- 参考元名をUIに出すか出さないか決まっている
- 参加人数の下限/上限が決まっている
- 必要な秘密情報が定義されている
- 初期データschemaが決まっている
- 最低限の初期データ件数が決まっている
- 勝敗条件がテスト可能な形に分解されている

## Definition of Done

1ゲーム完了の条件。

- トップ画面からゲーム開始できる
- 参加人数エラーが出せる
- スマホを回して秘密確認できる
- 途中で秘密情報が漏れない
- 最終結果まで進める
- 「もう一度遊ぶ」ができる
- 既存ゲームの動作を壊していない
- `npm run smoke` が通る
- `npm run typecheck` が通る
- `npm run build` が通る
- 必要なdocsとtask-listを更新している
- 追加時に入れた仮実装、重複コード、不要データを掃除するための残タスクが記録されている

## 最初に作るもの

最初は `ワード潜入者` を作る。

理由:

- 追加ゲームの中で最も小さく実装できる。
- 既存の受け渡し、秘密表示、投票、結果UIを流用しやすい。
- お題データの自作方針を検証しやすい。
- 友人テストで盛り上がりやすく、改善点を拾いやすい。
