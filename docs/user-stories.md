# ユーザーストーリー

## 目的

スマホ1台を友達同士で回して遊べる、ログイン不要のブラウザ向けパーティゲーム集を作る。
初期リリースでは以下のゲームを提供し、将来ゲームを追加しても既存ゲーム同士が干渉しない構造にする。

- 日本マップ当て
- ナンバートーク
- ワンナイト人狼
- 飲み会ゲーム辞典
- ワード潜入者
- インサイダー推理
- スパイロケーション
- 価値観メーター
- ランキング回答
- エセアーティスト
- みんなと同じ回答
- ワンワード協力クイズ

追加候補として、スマホ1台を回すことで秘密情報や投票を管理できるテーブルゲームを増やす。

## 前提

- 1台のスマホを参加者で順番に受け渡す。
- アカウント登録は行わない。
- 個人情報は入力させない。
- プレイヤーが設定できる情報はニックネームと担当色のみとする。
- 最大プレイヤー数は初期値として8人とする。
- 収益化は広告を主軸にする。
- 日本マップ当ての画像ソースはMapillaryを前提にする。
- ナンバートークは数字1から100、1人1枚、お題に沿った会話、並び順公開の流れを固定する。開始前に今回のお題を確認でき、合わない場合は同カテゴリ内で再抽選できる。
- ワンナイト人狼は基本役職の村人、人狼、占い師、怪盗を中心に、プレイヤー数+2枚、夜、昼、投票、勝敗判定の流れを採用する。
- 飲み会ゲーム辞典は道具なしで遊べるゲームのルールテキストを検索できるデータベースとする。
- 飲み会ゲーム辞典の通常カテゴリ表示は国だけにする。国が不明または特定しづらいものは未設定または国際扱いにする。
- 少し大人向けの会話ゲームだけ、例外として `下ネタ` 特別カテゴリを表示できる。ただし直接的な名前や説明は避ける。
- 飲み会ゲーム辞典はAI/cronで候補追加できるよう、別名、重複判定キー、参照元、レビュー日をデータに持つ。
- ワード潜入者は多数派には秘密語、潜入者にはカテゴリだけを表示し、ヒント、議論、投票、潜入者の最終推理で勝敗を判定する。
- インサイダー推理は進行役と内通者だけが答えを知り、質問、答え確定、内通者投票で勝敗を判定する。
- スパイロケーションはスパイ以外に場所を配り、質問、告発投票、スパイの場所推理で勝敗を判定する。
- 価値観メーターは2チームに分かれ、親チームは親だけが見た正解位置をヒントから推測し、相手チームは正解が推測より左右どちらかを予想する。後攻1点、10点先取、キャッチアップ、同点時のサドンデスを採用する。
- ランキング回答は各自の1-10の秘密番号に合わせた回答を出し、キャプテンが小さい順に並べて協力成否を判定する。
- エセアーティストは出題者を1人置き、出題者以外が線を描いたあと、偽物投票と偽物の最終推理で勝敗を判定する。
- みんなと同じ回答は全員が秘密回答し、正規化後の最多回答と一致したプレイヤーへ1点を与え、5問の合計点を競う。
- ワンワード協力クイズは回答者以外が秘密ヒントを入力し、重複ヒントと不適切なヒントを取り消してから、回答者が1回だけ答える。5問の正解数を記録する。
- 既存ゲームの名称、カード文面、UI、画像、音声、説明文をそのまま使う場合はライセンス確認または許諾取得を前提にする。
- 追加テーブルゲーム候補の原典調査と実装たたき台は `docs/table-game-expansion-spec.md`、実装順と詳細タスクは `docs/table-game-expansion-plan.md` と `docs/table-game-expansion-task-list.md` を参照する。

## ペルソナ

### ホスト

友達との集まりでスマホを出し、すぐにゲームを始めたい人。

### プレイヤー

自分のターンだけスマホを受け取り、秘密情報や回答を他人に見られずに遊びたい人。

### 運営者

個人情報を持たずにサービスを運用し、ゲーム追加や広告配置を安全に行いたい人。

### 開発者

新しいゲームを追加するときに、既存ゲームの状態管理、画面、ルール、保存データへ影響を与えたくない人。

## 共通ユーザーストーリー

### US-COM-001 ゲーム一覧を見る

As a ホスト  
I want ゲーム一覧から遊びたいゲームを選びたい  
So that その場の人数や気分に合うゲームをすぐ始められる

受け入れ条件:

- ゲーム一覧に初期ゲームが表示される。
- トップのゲームカードにはゲームタイトル、ゲーム内容、参加人数だけが表示される。
- 対応人数に満たないゲームは開始前に理由が表示される。

### US-COM-002 プレイヤーを登録する

As a ホスト  
I want ニックネームと担当色だけでプレイヤーを登録したい  
So that 個人情報なしで遊び始められる

受け入れ条件:

- 2人から8人まで登録できる。
- ニックネームは同一セッション内で識別できる。
- 担当色は重複しないように選べる。
- メールアドレス、電話番号、SNS連携、位置情報権限は要求しない。

### US-COM-003 スマホを安全に受け渡す

As a プレイヤー  
I want 自分のターン以外の秘密情報や回答が見えない状態でスマホを受け取りたい  
So that パスアンドプレイでも公平に遊べる

受け入れ条件:

- ターン開始前に「次は誰の番か」を示す受け渡し画面が表示される。
- 受け渡し画面では前プレイヤーの回答、役職、数字、結果が見えない。
- プレイヤーが明示的に開始操作をするまで秘密情報は表示されない。
- ブラウザバックやリロード時も直前の秘密情報が不用意に表示されない。

### US-COM-004 ゲーム結果を見る

As a プレイヤー  
I want ゲーム終了後に全員の結果を見たい  
So that その場で盛り上がれる

受け入れ条件:

- ゲームごとに適した結果画面が表示される。
- プレイヤー名と担当色で結果を識別できる。
- 結果画面から同じ設定でもう一度遊べる。
- 結果画面からゲーム一覧へ戻れる。

### US-COM-005 広告がゲーム進行を邪魔しない

As a プレイヤー  
I want 秘密情報や回答中に広告で操作を邪魔されたくない  
So that 誤タップや情報漏れを避けられる

受け入れ条件:

- 広告はホーム、ゲーム一覧、設定、ラウンド結果、最終結果を中心に表示する。
- 秘密情報表示中、投票中、回答中、受け渡し画面では広告を表示しない。
- 広告の読み込み失敗でゲーム進行が止まらない。

## 飲み会ゲーム辞典 ユーザーストーリー

### US-DRINK-001 道具なしゲームを探す

As a ホスト
I want 道具なしで遊べる飲み会ゲームを一覧から探したい
So that その場で次に遊ぶゲームをすぐ決められる

受け入れ条件:

- 飲み会ゲーム辞典がゲーム一覧の1項目として表示される。
- ルール説明のみで、勝敗判定や秘密情報の画面は持たない。
- ゲーム名、別名、ルール文で検索できる。
- 国と `下ネタ` 特別カテゴリで絞り込みできる。
- 表示カテゴリは原則として国だけにし、例外カテゴリは `下ネタ` のみとする。
- 秘密、恋愛、人物評価などへ踏み込む刺激強めのゲームも検索して選べる。
- 刺激強めのゲームは開始前に内容を表示し、回答拒否や途中終了ができる。

### US-DRINK-002 AIが重複を判断して追加できる

As a 運営者
I want AI/cronが新しい飲み会ゲーム候補を調査し、重複を避けて追加できるデータ構造にしたい
So that データベースを継続的に増やせる

受け入れ条件:

- 各ゲームに `id`、`title`、`aliases`、`hiddenAliases`、`country`、`specialCategory`、`rules`、`duplicateKey`、`aiReviewHint`、`sourceRefs`、`reviewedAt`、`intensity`、`contentWarnings` を持てる。
- 既存ゲームと同じ核のルールなら新規追加せず、別名や参照元を既存レコードへ追記する。
- 新規追加時はルール文を独自文言で要約し、外部サイト本文をコピーしない。
- 直接的な元ネタ名は `hiddenAliases` に入れ、UIへ表示しない。
- 道具を使うゲームは初期辞典には入れない。
- 道具やカード判定が核の候補は、辞典ではなく将来の実装候補として扱う。
- 人間関係へ踏み込むことだけを理由に候補を除外しない。

## 追加テーブルゲーム ユーザーストーリー

### US-TABLE-001 秘密情報をスマホで配る

As a ホスト
I want 役職、秘密ワード、場所、番号、正解位置をスマホで安全に配りたい
So that カードや紙がなくてもテーブルゲームを遊べる

受け入れ条件:

- 追加ゲームは1台のスマホを回して秘密情報を確認できる。
- 秘密情報の確認前後には受け渡し画面を挟む。
- 前のプレイヤーの秘密情報が次のプレイヤーに見えない。
- リロードやブラウザバックで秘密情報へ直接戻らない。

### US-TABLE-002 投票や推理をアプリで確定する

As a プレイヤー
I want 投票、推理、並び替え、採点をアプリ上で確定したい
So that 口頭進行だけより公平に結果を出せる

受け入れ条件:

- 投票があるゲームは、誰が誰に投票したかを結果画面で確認できる。
- 推理入力があるゲームは、正解/不正解と勝利陣営を表示できる。
- 採点があるゲームは、ラウンドごとの得点や失点を表示できる。
- 秘密投票中や推理入力中には広告を表示しない。

## 日本マップ当て ユーザーストーリー

### US-GEO-001 Guessrのゲーム設定を作る

As a ホスト  
I want ラウンド数と制限時間だけを設定したい  
So that 集まりの時間や難易度に合わせて遊べる

受け入れ条件:

- ラウンド数は3または5を選べる。
- 制限時間はなし、30秒、60秒、90秒などから選べる。
- 移動はNo Move固定とし、設定項目として表示しない。
- 地点デッキはユーザーに選ばせない。
- 出題地点は運営側が管理するMapillary地点データから選ばれる。

### US-GEO-002 同じ地点を全員に出題する

As a プレイヤー  
I want 1ラウンドで全員が同じ地点を見て回答したい  
So that 公平に競える

受け入れ条件:

- ラウンド開始時に1つのMapillary画像または地点が選ばれる。
- すべてのプレイヤーに同一ラウンド地点が出題される。
- 各プレイヤーの回答前に視点や地図状態が初期化される。
- 前のプレイヤーの回答ピン、距離、スコアは表示されない。

### US-GEO-003 Mapillary画像を見る

As a プレイヤー  
I want Mapillaryの画像を見ながら場所を推測したい  
So that 日本のどこかを当てる遊びができる

受け入れ条件:

- Mapillary画像がゲーム画面の主要領域に表示される。
- 画像読み込みに失敗した場合はリトライまたは代替地点に切り替わる。
- Mapillaryの必要な attribution や表示要件を満たす。
- 画像ソース固有の処理はGuessrゲーム内または画像プロバイダ層に閉じる。

### US-GEO-004 地図にピンを刺して回答する

As a プレイヤー  
I want 日本地図上にピンを刺して回答したい  
So that 推測地点を直感的に指定できる

受け入れ条件:

- 回答用地図は日本全体を対象にする。
- プレイヤーはピンを置き直せる。
- 回答確定前に確認操作がある。
- 回答確定後はそのプレイヤーの回答を編集できない。

### US-GEO-005 ラウンド結果を見る

As a プレイヤー  
I want 全員の回答後に正解地点、各ピン、距離、点数を見たい  
So that 誰が近かったかで盛り上がれる

受け入れ条件:

- 正解地点と全プレイヤーの回答ピンが表示される。
- プレイヤーごとの距離が表示される。
- プレイヤーごとのラウンド点数が表示される。
- 次ラウンドへ進める。

### US-GEO-006 地点データを管理できる

As a 運営者  
I want Mapillary地点を内部データとして管理したい  
So that 遊べる品質の地点だけを出題できる

受け入れ条件:

- 地点にはMapillary画像ID、緯度経度、難易度、タグ、地域、利用可否を持てる。
- 壊れた画像や不適切な画像は無効化できる。
- ユーザーには地点データやデッキ選択を表示しない。
- 将来の運営機能として地域やタグで出題対象を絞れる。
- ゲーム中にMapillaryの生データ構造へ直接依存しない。

## ナンバートーク ユーザーストーリー

### US-ITO-001 ナンバートークのゲーム設定を作る

As a ホスト  
I want お題カテゴリと会話時間だけを設定したい  
So that 参加者に合ったお題で遊べる

受け入れ条件:

- 数字範囲は1から100で固定する。
- 手札は1人1枚で固定する。
- テーマ文はオリジナルの文言として管理する。
- お題カテゴリは通常、変化球、恋愛などを選べる。

受け入れ条件:

### US-ITO-003 会話フェーズを進める

- 必要に応じて会話タイマーを表示できる。

### US-ITO-004 並び順を決めて公開する

As a プレイヤー  
I want 全員で決めた順番をアプリ上で並べて公開したい  
So that 成功失敗を判定できる

受け入れ条件:

- プレイヤーをドラッグまたはタップで並べ替えられる。
- 公開前に確認操作がある。
- 公開後に全員の数字が表示される。
- 昇順または降順の正誤が判定される。

## ワンナイト人狼 ユーザーストーリー

### US-WOLF-001 役職セットを作る

As a ホスト  
I want 人数に合った基本役職セットで開始したい  
So that ルール破綻なくゲームを開始できる

受け入れ条件:

- 3人から8人で開始できる。
- 使用カードはプレイヤー数+2枚とする。
- 初期役職は村人、人狼、占い師、怪盗を使う。
- 3人から6人では、人狼2枚、占い師1枚、怪盗1枚、残りを村人として構成できる。
- 説明文や画面文言は権利確認済みの文言、または独自文言で管理する。
- 役職追加時に既存役職の処理へ影響しない。

### US-WOLF-002 自分の役職を確認する

As a プレイヤー  
I want 自分の役職だけをこっそり確認したい  
So that 正体隠匿ゲームとして成立する

受け入れ条件:

- 受け渡し画面の後、自分の役職だけが表示される。
- 役職説明はその場で確認できる。
- 確認後は役職を隠して次のプレイヤーへ渡せる。
- 誰にも配られなかった2枚は中央カードとして扱う。

### US-WOLF-003 夜行動を行う

As a プレイヤー  
I want 自分の役職に応じた夜行動を秘密裏に行いたい  
So that 役職能力を使って推理材料を得られる

受け入れ条件:

- 全プレイヤーが順番に夜フェーズ画面を確認する。
- 夜行動は占い師、人狼、怪盗の順に進む。
- 村人など行動がない役職でも、他人から役職を推測されにくい進行にする。
- 占い師は他プレイヤー1人、または中央カード2枚を確認できる。
- 人狼は他の人狼を確認できる。
- 怪盗は自分と他プレイヤー1人のカードを交換できる。
- 夜行動の結果は必要なプレイヤーにだけ表示される。
- 夜行動の状態はこのゲームのセッション内に閉じる。

### US-WOLF-004 議論と投票を行う

As a プレイヤー  
I want 議論時間の後に投票したい  
So that 多数決で勝敗を決められる

受け入れ条件:

- 議論タイマーを表示できる。
- 投票はプレイヤーごとに秘密入力できる。
- プレイヤー内に人狼がいないと思う場合に平和村へ投票できる。
- 全員投票後に投票結果を公開する。
- 同票などの処理ルールが明示される。

### US-WOLF-005 勝敗を判定する

As a プレイヤー  
I want 最後に役職、投票、勝敗を見たい  
So that ゲームの結末を納得して楽しめる

受け入れ条件:

- 全員の役職が公開される。
- 中央カードが公開される。
- 投票先が公開される。
- 勝利陣営または勝利プレイヤーが表示される。
- 最多得票者に人狼が含まれる場合は人間チーム勝利とする。
- 最多得票者が人間のみの場合は人狼チーム勝利とする。
- 全員の投票が分散して処刑なしの場合、人狼が場にいなければ全員勝利、人狼が場にいれば人狼チーム勝利とする。
- 同じ設定でもう一度遊べる。

## ゲーム追加と分離のためのユーザーストーリー

### US-EXT-001 ゲームを独立モジュールとして追加する

As a 開発者  
I want 新しいゲームを独立したモジュールとして追加したい  
So that 既存ゲームの実装を変更せずにゲーム一覧へ追加できる

受け入れ条件:

- 各ゲームは一意の `gameId` を持つ。
- 各ゲームはタイトル、対応人数、設定スキーマ、開始処理、画面ルートを自己申告する。
- ゲーム一覧は登録されたゲーム定義から生成される。
- 新規ゲーム追加時に既存ゲームの内部状態へ直接アクセスしない。

### US-EXT-002 ゲームごとに状態を分離する

As a 開発者  
I want ゲームごとの状態を名前空間で分離したい  
So that あるゲームの保存データや進行状態が他ゲームを壊さない

受け入れ条件:

- 保存キーは `gameId` と `sessionId` を含む。
- 共通プレイヤー情報とゲーム固有状態を分離する。
- ゲーム固有状態はそのゲームの reducer または state machine だけが更新する。
- 他ゲームの型や保存データへ依存しない。

### US-EXT-003 共通機能だけを共有する

As a 開発者  
I want 受け渡し、プレイヤー、タイマー、広告、保存処理だけを共通化したい  
So that ルールや画面はゲームごとに独立させられる

受け入れ条件:

- 共通モジュールはゲームルールを知らない。
- ゲームは共通APIを通じてプレイヤー情報、保存、広告表示可否、タイマーを利用する。
- 共通モジュールから特定ゲームへの import を禁止する。
- ゲーム間で直接イベントを送らない。

### US-EXT-004 ゲーム固有の広告制御を登録する

As a 開発者  
I want ゲームごとに広告表示禁止フェーズを宣言したい  
So that 秘密情報や回答中に広告が表示されない

受け入れ条件:

- 各ゲームは現在フェーズが広告表示可能かを返せる。
- 共通広告コンポーネントはその値に従う。
- 秘密表示、回答中、投票中は初期3ゲームすべてで広告禁止とする。

## 非機能要件ストーリー

### US-NFR-001 個人情報を保存しない

As a 運営者  
I want 個人情報を保存せずに運用したい  
So that ユーザーの心理的ハードルと管理リスクを下げられる

受け入れ条件:

- アカウント登録を提供しない。
- ニックネームと担当色は端末内セッションデータとして扱う。
- サーバーへ送るデータは必要最小限にする。
- 分析を行う場合は個人を識別しない集計イベントに限定する。

### US-NFR-002 スマホで快適に動く

As a プレイヤー  
I want スマホのブラウザでスムーズに遊びたい  
So that アプリを入れずにその場で参加できる

受け入れ条件:

- 縦画面スマホで主要操作が完結する。
- タップ対象は誤操作しにくい大きさにする。
- 画像読み込み中や通信失敗時の状態を表示する。
- 低速回線でもゲーム進行が破綻しない。

### US-NFR-003 オフラインに近い体験を保つ

As a ホスト  
I want 一度読み込んだ後はゲーム進行が通信に依存しすぎないようにしたい  
So that 集まりの場で通信が不安定でも遊べる

受け入れ条件:

- 画像や地図が必要なGuessr以外は、基本進行を端末内で完結できる。
- 共通UIとゲームロジックはPWAとしてキャッシュできる。
- 通信必須の箇所はユーザーにわかる形で読み込み状態を出す。
